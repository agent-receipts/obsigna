## Executive Summary

The agent security space has matured past "can we intercept the agent?" into "can we prove what it did, in a form a third party will accept?" Every enforcement approach — MCP proxying, egress firewalling, kernel-level enforcement, application-level policy engines, and enterprise gateways — has at least one serious implementation.

The decisive shift in 2026 is **provenance**: signed, hash-chained receipts went from a differentiator to table stakes. What now separates projects is the **trust boundary** — whether the process that signs the audit trail is the same process being audited — and whether the record is **portable** enough for an external verifier.

The development to watch in June is **cross-channel correlation**. Pipelock now carries HTTP, WebSocket and MCP traffic in a single firewall-scoped evidence log, and Canyon Road's Watchtower has offered cross-channel correlation commercially. Correlating an agent's whole session is no longer an unoccupied gap; it is being occupied from different vantages, and the open questions are which channels each vantage can reach and whether the record leaves the tool that produced it.

The space segments into five layers:

| Layer | What it does | Key players |
|---|---|---|
| **MCP Gateways** (commercial) | Managed proxy for MCP traffic with auth, audit, rate limiting | MintMCP, Peta, TrueFoundry, Lasso, Gravitee, Traefik Hub |
| **Agent Firewalls** (open-source) | Intercept + scan agent traffic (MCP and/or HTTP) | Pipelock, mcp-firewall (ressl), mcp-firewall (dzervas) |
| **Kernel-Level Enforcement** | OS-level syscall interception, sandboxing | agentsh / Canyon Road, Anthropic sandbox-runtime |
| **Governance Frameworks** | Application-level policy engine, identity, compliance | GitHub Agentic Workflows, MetaComp StableX KYA (regulated finance) |
| **Audit & Provenance** | The provenance record *is* the product | Agent Receipts, nono, Asqav, InALign |

A note on two baseline entries we have corrected this cycle:

- **Microsoft Agent Framework is not an agent-audit toolkit.** Earlier landscape reads listed a "Microsoft AGT / Agent Governance Toolkit" with signed receipts, a "Decision BOM," and in-process signing. On re-checking the source, that repository is the Microsoft Agent Framework — the Semantic Kernel and AutoGen successor for building and orchestrating multi-agent workflows. Its work is MCP skills discovery, A2A sessions, Foundry hosting, evals, default-on OpenTelemetry instrumentation, and a Microsoft Purview integration (`agent-framework-purview`). That is observability and orchestration with a governance tie-in, not a signed-receipt format. We have removed it from the audit/governance comparisons below. If a distinct Microsoft agent-audit toolkit exists, we will re-add it when it can be pointed at.
- **"Agent Wall" is unverified.** The MCP-proxy "Agent Wall" tracked in earlier matrices could not be re-located this cycle; `agentwall.tech` resolves to a different product (an enterprise anti-scraping / paywall firewall). The entry is removed pending re-sourcing.

## Audit & Provenance Layer

The category that crystallized in May 2026: tools whose primary product is the provenance record rather than enforcement. The differentiating axis is **where the signing key lives** (inside vs. outside the audited process) and **how portable** the record is.

| | Primary product | Signing locus | Envelope | Where your data lives | Cost | Notes |
|---|---|---|---|---|---|---|
| **Agent Receipts** | Provenance record | **Out-of-agent daemon** | W3C VC (Ed25519, RFC 8785) | Local by default — your machine; optional self-host or outsource | Free, local-first | Keys + chain outside the audited process; one chain across MCP, hook (native tools) and HTTP; web/WASM verifier checks receipts in-browser with nothing leaving the machine |
| **nono** | Provenance record | **Out-of-process** (append-only Merkle log) | Sigstore/Rekor anchored | Local log, anchored to the public Rekor transparency log | Free (open source) | Closest on the boundary axis; binary-identity binding; latest release v0.55.0 (2026-05-17), no movement since |
| **Asqav** | Provenance record | **Server-side / custodial** (hosted) | Signed records (ML-DSA-65, RFC 3161 timestamps) | Server-side — keys + signing on Asqav (API key required); only a hash + metadata sent by default, self-host option for full payloads | Free tier; Pro $39/mo, Business $149/mo | Remote-custodial — all ML-DSA runs server-side; the SDK is a thin client. Threshold ML-DSA, SD-JWT tokens, DORA + EU AI Act reporting |
| **InALign** | Alignment + audit | In-process (+ optional external anchor) | SHA-256 hash chain + W3C PROV graph | Local chain, optional external anchor | Free (open source) | Optional `inalign-anchor` anchors the chain root externally; 32 MCP tools, MITRE ATT&CK/ATLAS mapping |

> The axis that matters is in-agent vs. out-of-agent signing and record portability. On the first question, **nono lands on the same side as Agent Receipts**, so the differentiation runs through the portable [W3C VC](/specification/overview/) envelope and the single cross-channel chain. Two corrections this cycle: **Asqav** signs server-side as a hosted custodial service, not in-agent; **InALign** adds a W3C PROV knowledge graph and an optional external anchor, but PROV is the provenance-graph model, not the Verifiable Credential envelope — the VC envelope is still unique to Agent Receipts in this set. See [the audit boundary belongs outside the agent](/blog/daemon-process-separation/) for why the boundary is the durable property.

**Data sovereignty.** Where the data lives is also a jurisdiction question. A local-first trail stays on the operator's machine with no third-party processor. A hosted custodial signer introduces a processor under the vendor's jurisdiction even when only hashes are transmitted, since keys, signing, and transmitted metadata sit on vendor infrastructure. This bears on data-residency and processor-disclosure obligations (EU AI Act, DORA).

**Convergence from the firewall layer.** Pipelock (an agent firewall, below) now emits **Audit Packet v0** — a portable record canonicalised with RFC 8785 JCS, with first-party verifiers in Go, TypeScript and Rust, plus an in-toto agent-action-receipt predicate (DSSE-wrapped) and a SCITT signed-statement profile. Its primary product is still the firewall, but its evidence story has moved squarely into this layer's territory. That is convergence on shared primitives rather than a competing audit-first product.

## Architectural Approaches Compared

| Approach | Enforcement guarantee | Bypass risk | Setup complexity | Coverage scope |
|---|---|---|---|---|
| **Kernel-level** (agentsh) | Strongest — syscall interception | Very low (requires kernel exploit) | High (kernel 6.7+, FUSE, capabilities) | Shell, filesystem, network, processes |
| **Egress proxy** (Pipelock) | Strong for network — capability separation | Medium (agent could use alternative channels) | Low (single binary) | HTTP + WebSocket egress, MCP responses |
| **MCP stdio proxy** (mcp-firewall) | Moderate — protocol-level interception | Medium (only covers MCP channel) | Low (wrap command) | MCP tool calls and responses only |
| **Hook-based** (dzervas/mcp-firewall) | Moderate — pre-execution check | Medium (depends on client enforcement) | Very low | Tool calls in supported clients |

*Audit & provenance tools are not enforcement tools — they record rather than block. The analogous axis for them is the trust boundary: an in-process signer shares the agent's blast radius; an [out-of-agent signer](/blog/daemon-process-separation/) does not.*

## Key Primitives Convergence

Multiple projects have independently converged on the same cryptographic and protocol primitives. By mid-2026, signed hash-chained receipts are no longer differentiating — they are table stakes. The receipt-format conversation is consolidating around a shared set of canonicalisation and transparency primitives.

| Primitive | Used by |
|---|---|
| **Ed25519 signing** | Pipelock, mcp-firewall (ressl), nono, Agent Receipts |
| **SHA-256 hash chaining** | mcp-firewall (ressl), InALign, Agent Receipts |
| **RFC 8785 JCS canonicalisation** | Agent Receipts, Pipelock (Audit Packet v0); also draft-sharif and x402-delegation drafts |
| **ML-DSA-65** (post-quantum) | Asqav (server-side, threshold m-of-n) |
| **Signed, hash-chained receipt** (any scheme — *table stakes*) | Agent Receipts, Pipelock (Audit Packet v0), Asqav, nono, InALign |
| **W3C Verifiable Credentials** (data model envelope) | Agent Receipts only — competitors sign with other schemes (Asqav: ML-DSA-65; nono: Sigstore/Rekor; Pipelock: Audit Packet/JCS; InALign: SHA-256 + W3C PROV graph), not the VC envelope |
| **in-toto / DSSE predicate + SCITT signed-statement** | Pipelock (CAP-SRP is SCITT-aligned, adjacent) |
| **Sigstore / Rekor transparency log** | nono |
| **SD-JWT selective disclosure** | Asqav (Verifiable Intent, adjacent) |
| **SPIFFE actor identity** | Pipelock |
| **Multi-language verifiers** | Pipelock (Go/TS/Rust); Agent Receipts (Go/TS/Py + browser WASM) |
| **DIDs (Decentralized Identifiers)** | Agent Receipts |
| **OPA/Rego policies** | mcp-firewall (ressl); OpenKedge (Cedar/OPA packs, adjacent) |
| **OWASP Agentic AI Top 10** | Pipelock, mcp-firewall (ressl) |
| **Out-of-agent signing / log** | Agent Receipts (daemon owns keys + chain); nono (append-only log the agent can't reach); Pipelock's 3-UID containment gives its proxy partial separation; most others sign in-process |
| **Hook-based emission** | Claude Code (full tool-surface coverage), Codex CLI (partial — no WebSearch, partial shell); Agent Receipts aligns with both hook surfaces |

## Standards Window

EU AI Act **Article 12** requires automatic, tamper-resistant logging of high-risk AI system operation over its lifetime — nearly verbatim, the problem a hash-chained, independently-signed receipt solves.

The regulatory clock moved this cycle without moving the live deadline:

- **Article 12 and the Article 9–17 / Article 26 obligations apply from 2 August 2026.** That date is unchanged.
- The **Digital Omnibus on AI** reached provisional political agreement on 6–7 May 2026, was confirmed by Council Member State representatives on 13 May, and was formally endorsed by the European Parliament on 16 June. Formal adoption and Official Journal publication are expected in July 2026.
- *Once adopted*, the Omnibus defers some obligations: standalone Annex III high-risk to 2 December 2027, Annex I (embedded in regulated products) to 2 August 2028, and the Article 50(2) synthetic-content watermarking duty to 2 December 2026. It also adds an Article 5 prohibition on AI-generated NCII and CSAM.
- **Until Official Journal publication, 2 August 2026 remains the legally live date.** No finalised harmonised technical standard for Article 12 logging exists yet — `prEN 18229-1` (AI logging + human oversight) and `ISO/IEC DIS 24970` (AI system logging) are both incomplete.

A growing set of format and protocol efforts is positioning into that space. None is IETF working-group-adopted; the IETF entries are individual Internet-Drafts. The Momentum column flags which are advancing and which are dormant placeholders.

| Effort | Venue | What it is | Maturity | Momentum |
|---|---|---|---|---|
| **Audit Packet v0** | Pipelock | Receipt format (RFC 8785 JCS) with Go/TS/Rust verifiers, in-toto/DSSE predicate + SCITT profile | Shipping | **Active** — v2.4→v2.6 this spring |
| **W3C VC Data Integrity** | W3C | The envelope our receipts use; the CG argues canonicalisation (JSON-LD vs. RFC 8785) | Recommendation | **Stable** — published standard |
| **draft-sharif-agent-audit-trail** | IETF | Hash-chained agent-action log, trust levels L0–L4 | Individual I-D (-00) | **Stalled** — no update this cycle |
| **draft-marques-asqav-compliance-receipts** | IETF | Multi-jurisdiction compliance profile of signed action receipts | Individual I-D (-05) | **Active** — advanced to -05 (May 2026) |
| **draft-nivalto-agentroa-route-authorization** | IETF | BGP-ROA-modelled scope authorisation with per-hop + execution receipts | Individual I-D (-01) | **Quiet** — -01 since April |
| **draft-nelson-agent-delegation-receipts** | IETF | User-signed delegation receipts with a model-state commitment | Individual I-D (-10) | **Active** — -10 (Jun 2026) |
| **draft-stone-vcap-ap2-binding** | IETF | VCAP escrow settlement bound to Google's AP2 (commerce) | Individual I-D (-00) | **Early** — -00 (Mar 2026) |
| **W3C AIVS Community Group** | W3C | Agent integrity verification, session-grained rather than action-grained | Early-stage Community Group (SwarmSync.AI) | **Active (early)** — spec PR converging |

General supply-chain transparency work (IETF SCITT, COSE receipts) is the substrate some of these build on; several agent-audit efforts now profile SCITT directly.

Agent Receipts' position: the receipt is a W3C VC; the differentiator is the [out-of-agent boundary](/blog/daemon-process-separation/) plus one chain across channels; the format should be portable, and we will align with a credible standard rather than fork one.

## Gap Analysis

Areas that remain underserved despite the crowded landscape. Where a gap is closing, the closest approaches are named — this is no longer an empty-box exercise.

| Gap | Description | Who's closest |
|---|---|---|
| **Audit independent of the audited process** | Signing keys/log held outside the agent so the trail survives a compromised agent | Agent Receipts (daemon process separation) and nono (append-only log the agent can't reach); Pipelock's 3-UID containment now gives its proxy partial separation; most other audit-first tools still sign in-process |
| **Unified cross-channel audit** | Correlating MCP calls + REST calls + shell commands + native tool actions into one timeline per session | *Closing.* Agent Receipts (one daemon, one chain across MCP, hook and HTTP, out-of-path, attestation-only); Pipelock (HTTP + WebSocket + MCP in one firewall-scoped evidence log, in-path); Canyon Road Watchtower (commercial/closed, kernel vantage) |
| **Native host-tool plane** | The file edits and commands a runtime makes through its own native tools, invisible to in-path proxies watching MCP or egress | Agent Receipts (the hook plane is bound into the same chain as the proxied channels); in-path proxies do not see this surface |
| **HTTP/OpenAPI interception** | Policy-enforced proxy for agent REST/HTTP calls (not just MCP) | *Closing.* Pipelock now matches outbound HTTP API operations at the operation level, including GraphQL mutation root fields; agentsh proxies the network at kernel level |
| **Browser automation governance** | Intercepting Puppeteer/Playwright/CDP actions with policy enforcement | Underserved. Pipelock's operation-level egress covers the HTTP calls a browser driver makes but not CDP/Playwright semantics; agentsh governs the driver process at the syscall level. CDP-aware policy remains the thin spot |
| **CISO-ready reporting** | PDF/HTML reports a security team can review to approve agentic AI adoption | mcp-firewall (ressl) has compliance reports; Asqav produces EU AI Act / DORA audit packs (custodial); turnkey, tool-neutral CISO artifacts are still thin |
| **Policy portability standard** | A way to express agent policies that works across tools | No cross-tool policy standard exists; the record-format side is consolidating (RFC 8785 JCS, in-toto/SCITT) ahead of the policy side |
| **Agent identity federation** | Verifying agent identity across organizational boundaries | SPIFFE actor identity (Pipelock) and DID/passport efforts (AgentROA scope authorisation, AEOESS) are early |
